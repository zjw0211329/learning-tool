# 05 双 AI 协作约定（ZCode × Qoder）

> 生效日期：2026-09-19 · 本约定对所有在这个仓库工作的 AI 与人类有效

## 1. 分工

| 角色 | 承担者 | 职责 |
|---|---|---|
| 主开发 | **ZCode** | 功能设计、编写代码、自查测试、**本地提交**（`[zcode]` 前缀） |
| 审查者 | **Qoder** | 代码审查、调试修复、提交修复（`[qoder]` 前缀）、**审查通过后统一推送 GitHub** |
| 决策者 | 用户 | 需求取舍、版本范围、冲突仲裁 |

## 2. Git 约定

1. **提交信息前缀**：ZCode 用 `[zcode]`，Qoder 用 `[qoder]`，用户提交无前缀。例：
   `[zcode] V2.0：番茄钟 + 数据导入导出 + 排序移动`、`[qoder] fix: 导入校验缺少 status 白名单`
2. **推送权只属于 Qoder**（2026-09-19 用户裁决）：ZCode 只本地 commit，不执行 `git push`；
   Qoder 跑通 `tests/api_smoke.py` 与浏览器冒烟后统一推送。这样进 `main` 的内容都过了一遍验证，
   也从根上避免了双方各自推送导致的分叉与冲突仲裁。
3. **开工先同步**：任何一方开始工作前先 `git pull --rebase`，避免分叉。
4. **推送被拒时**：`git pull --rebase` 解决后再推；若产生实质冲突（同一文件同一处都改了），**停止推送**，由用户裁决保留哪一版。
5. **每次提交保持可运行**：不留半成品（实在要存档用 `wip:` 前缀，且不推送）。

## 3. 质量约定

1. 任何功能改动必须跑通 `tests/api_smoke.py`（默认临时库模式零副作用，无需起服务；推前门禁另测真实服务模式）。
2. 审查发现的问题：小修（错别字、空指针、参数校验）审查者可直接修并提交 `[qoder] fix: ...`；设计级分歧（数据结构、接口形状）写入 `docs/` 或交给用户裁决，不要私下改设计。
3. **隐私红线**：`app/data/`（学习日志数据库）永远不入库、不上传；`.gitignore` 中已有规则，不得移除。
4. **SQL 拼接边界**：`swap_order` 等辅助函数用 f-string 拼接的表名/列名只能是代码内常量，永远不允许把请求参数拼进 SQL 文本；新增同类函数必须保持这条边界。
5. **日期口径**：库内日期一律为规范 `YYYY-MM-DD` 字符串；导入等入口用「`date.fromisoformat` 解析后 round-trip 相等」校验，拒绝可解析但不规范的形式（如 ISO 周日期 `2026-W01-1`）。
6. **共享状态的入口对称性**（2026-09-20，V3 导航缺陷沉淀）：给某个视图加「自动选中 / 默认值」类便利逻辑时，必须同时检查所有共享同一状态的入口（当时是三个标签共享 `currentId`，只补了「复习」漏了另两个，用户实测才撞出来）。这类「不对称的第三条路径」后端门禁抓不到——接口全对、断言全绿——只有真实使用路径能暴露，审查时对"只改了一个入口"的便利性补丁保持警觉。

## 4. 流程文档

功能迭代按《01 调研 → 04 迭代计划 → 实现 → tests 回归 → 推送》推进；每版迭代计划单独成文（docs/04 是 V2，下一版 V3 起 docs/06 顺延）。

## 5. 沟通约定（2026-09-19 用户裁决）

任何一方回复用户时，必须用 **【给 <对方>】** / **【给你的】** 标注段落归属（`<对方>` 换成接收方名字，如【给 Qoder】/【给 ZCode】）：

- **【给 <对方>】**：跨 AI 的技术信息——审查结论回应、修复说明、代码交接（本地领先远程的提交号）、待办与验证请求；
- **【给你的】**：进度汇报、需要用户决策/操作的事项、产品与使用层面的说明。

用户负责在两个 AI 之间转述标注段落；未标注的内容默认给用户。
