## 2. 功能需求 FR9

- FR9.1 卡片 CRUD：正面/反面文本，归属某方向（与日志同构）；在「复习」视图内管理。
- FR9.2 复习队列：到期复习卡（due ≤ now）优先；新卡按每日上限（默认 10，可配）进入队列。
- FR9.3 复习交互：显示正面 → 翻面 → 四级评分按钮「忘记 / 困难 / 良好 / 简单」。
- FR9.4 调度：FSRS-6 官方算法，`desired_retention=0.9`；评分后写回卡片状态与到期时间。
- FR9.5 复习记录：每次评分落 `review_logs`（评分、时间），为后续统计与参数优化留数据。
- FR9.6 复习统计：复习视图顶部计数——今日待复习 / 今日新卡 / 今日已完成 / 卡片总数。
- FR9.7 示例数据：`/api/demo` 附带 6 张嵌入式知识卡（含少量已到期与未来到期），便于演示与验收。

## 3. 数据模型与迁移（首次结构变更）

```
cards(id INTEGER PK, direction_id INTEGER NOT NULL REFERENCES directions ON DELETE CASCADE,
      front TEXT NOT NULL, back TEXT NOT NULL DEFAULT '',
      fsrs TEXT NOT NULL,              -- 官方 Card.to_dict() 的 JSON 全量状态
      due TEXT NOT NULL,               -- 从 fsrs 提取的到期时间（UTC ISO 8601），供索引与排序
      created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')))

review_logs(id INTEGER PK, card_id INTEGER NOT NULL REFERENCES cards(id) ON DELETE CASCADE,
            rating INTEGER NOT NULL CHECK(rating IN (1,2,3,4)),
            reviewed_at TEXT NOT NULL,  -- UTC ISO 8601
            created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')))
```

- **迁移策略：additive-only**。SCHEMA 全部 `CREATE TABLE IF NOT EXISTS`，现有 `init_db()` 在每次启动时执行，v2.0 老库下次启动自动补建两张新表，**无 ALTER、无停机**，老数据不受影响。索引：`cards(direction_id, due)`、`review_logs(card_id, reviewed_at)`。
- 卡片调度状态整体存 JSON（官方 `Card.to_dict()/from_dict()`），`due` 冗余成列只为队列查询；两者以 fsrs 库为唯一事实源。

## 4. FSRS 接入决策

- **采用官方 py-fsrs 6.3.2**（PyPI 包名 `fsrs`，MIT；实测本机可装，仅依赖 typing-extensions）。`requirements.txt` 增加一行。
- 实测 API（v6）：`Scheduler(review_card(card, rating, review_datetime=None) -> (Card, ReviewLog))`；新卡初始 `State.Learning`，带 `learning_steps/relearning_steps`。
- 默认 21 参数 + `desired_retention=0.9`，不做参数调优 UI。
- **测试确定性**：`Scheduler(enable_fuzzing=False)`（默认开启随机抖动，测试必须关闭）。
- 时间统一 **UTC 存储**、前端转本地显示（fsrs 内部使用 tz-aware UTC datetime）。
- 评分映射：忘记=Rating.Again、困难=Rating.Hard、良好=Rating.Good、简单=Rating.Easy。

## 5. API 变更（新增）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | /api/directions/{id}/cards | 卡片列表（含 state/due） |
| POST | /api/directions/{id}/cards | 新建 `{front, back?}` |
| PATCH/DELETE | /api/cards/{id} | 编辑 / 删除 |
| GET | /api/directions/{id}/review/queue | 今日队列：到期卡 + 新卡（按上限截取）+ 计数 |
| POST | /api/cards/{id}/review | `{rating: 1..4}` → FSRS 调度、写回、落 review_logs |

校验沿用表驱动思想：cards 的导入/入参用 `_BACKUP_SPEC` 同款风格（届时把 cards 纳入导出/导入备份，spec 各加行，导出版本号随 v3 升至 2）。

## 9. 测试与验收

1. **调度行为锁定**（`enable_fuzzing=False`）：同一张卡连续评 Good，due 间隔单调增长；评 Again 后 due 落在学习步内（分钟级）。
2. **队列语义**：新卡上限生效（12 张卡、上限 10 → 队列 10）；到期卡评分后移出当日队列；明日到期卡不出现在今日队列。
3. **迁移**：用 v2.0 形态旧库启动 → 两张新表自动创建、旧数据完整可查（验收脚本化到 tests）。
4. **备份兼容**：v2.0 备份导入 v3 库成功（无 cards 数据）；v3 备份含 cards 且可回灌；导出版本号升至 2，v3 备份拒绝被 v2.0 语义导入的场景明确报错。
5. **浏览器**：建卡 → 复习完整流程 → 计数变化；卡片增删改即时反映。
6. 原有 96（临时库）/ 54（真实服务）门禁回归全绿；cards 相关新断言按 docs/05 §3 补入同一测试文件。
